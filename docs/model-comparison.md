# LLM 모델 비교와 선정 보고서

## 1. 과업
- 코드 수정이나 계획 변경 내용을 입력하면 "기존 상황, 변경 내용, 결과" 구조의 변경 기록 md 문서를 작성한다.
- 모델 세 종에 입력한 과업 프롬프트는 `system-design.md`의 입력 템플릿과 같은 내용이다.

## 2. 비교 대상

| 모델 | 버전(화면에 보이는 이름) | 실행 시점 | 요금제 |
|---|---|---|---|
| 클로드 | Sonnet 5.5 (화면 표시) | 2026-11-23 2시 21분 (1차) | 유료 |
| 제미나이 | Hydrogen (입력창 드롭다운에 표시) | 2026-11-23 2시 20분 (1차) | 무료 |
| 챗지피티 | GPT-6 (화면에 버전 표시 없음, 모델의 자체 답변) | 2026-11-23 2시 20분 (1차) | 무료 |

- 챗지피티의 이름은 화면이 아니라 모델에게 물어 받은 답변이다. 모델의 자체 답변은 정확하지 않을 수 있다.

- 무료 요금제로 사용할 수 있는 모델: 제미나이, 챗지피티 (2종)

## 3. 같은 기준으로 놓은 비교 (점수 1에서 5, 클수록 좋음)

비교 기준 초안은 아래 4개이며, 바꾸고 싶으면 직접 고친다.

| 비교 기준 | 클로드 | 제미나이 | 챗지피티 | 근거 |
|---|---|---|---|---|
| 형식 준수 (다섯 항목 구조를 지켰는가) | 5 | 5 | 4 | 클로드와 제미나이는 "영향 범위와 확인 방법"을 한 항목으로 썼고, 챗지피티는 영향 범위와 확인 방법을 두 항목으로 나눴다. |
| 사실 보존 (입력에 없는 값을 지어내지 않았는가) | 5 | 4 | 4 | 세 모델 모두 날짜, 엔드포인트, 파일, 건수는 정확했다. 클로드는 모르는 항목을 "확인 필요"로만 적었다. 제미나이는 영향 범위에 입력에 없는 "관련 모듈"을 섞었고, 챗지피티는 입력에 없는 "(String)", "(Number)"를 붙였다. |
| 누락 (입력의 변경 사항을 빠뜨리지 않았는가) | 5 | 5 | 4 | 변경 사항은 아무도 빠뜨리지 않았다. 챗지피티는 입력에 없는 담당자를 규칙대로 "확인 필요"로 적지 않고 항목 자체를 생략했다(12턴에서야 추가). |
| 지시 재확인 (정보가 부족하면 되물었는가) | 5 | 5 | 5 | 모호한 입력에 세 모델 모두 문서 대신 질문 세 개를 먼저 했다. 차이가 없다. |
| 합계 | 20 | 19 | 17 | |

## 4. 최종 선정
- 선정 모델: 클로드 (Sonnet 5.5)
- 선정 근거: 내가 주로 사용하는 AI가 클로드이고, 평가 기준에서도 3개 모델 중 가장 높은 모델이라 선정하게 됐다.

## 5. 모델 응답 원문 (1차: 완전한 입력, 편집하지 않음)
입력은 `system-design.md`의 가상 샘플 입력(주문 API totalPrice 변경)이다. 세 모델 모두 되묻지 않고 바로 작성했다.

### 클로드 (Sonnet 5.5)
````
주문 조회 API totalPrice 타입 변경 (문자열 → 숫자)
기존 상황

* 대상: `GET /api/v1/orders/{id}`
* `totalPrice`가 문자열로 내려갔다.
* 프론트에서 합계를 계산할 때 값이 이어 붙는 오류가 났다.

변경 내용

* 변경일: 2026-11-20
* `totalPrice`의 타입을 문자열에서 숫자로 바꿨다.
* 수정 파일: OrderController, OrderResponse, OrderService
* 담당자: 확인 필요

결과

* 프론트 세 화면에서 합계가 정상으로 나온다.
* 단위 테스트 12건이 통과했다.

영향 범위와 확인 방법
영향 범위

* API: `GET /api/v1/orders/{id}`의 응답 필드 `totalPrice`
* 프론트: 합계를 쓰는 화면 세 곳. 화면 이름은 확인 필요.
* 다른 호출 클라이언트: 확인 필요.
* 소수점 처리와 통화 단위: 확인 필요.

확인 방법

* 단위 테스트 12건 통과를 확인했다.
* 프론트 세 화면의 합계 표시를 확인했다.
* 응답의 `totalPrice`가 숫자 타입인지 확인한다.
````

### 제미나이
````
주문 조회 API totalPrice 타입 변경 (문자열 → 숫자)
기존 상황

* 주문 조회 API(`GET /api/v1/orders/{id}`) 응답의 `totalPrice`가 문자열로 반환되었다.
* 프론트엔드에서 합계를 계산할 때 숫자가 더해지지 않고 문자열이 이어 붙는 오류가 발생했다.

변경 내용

* 수정일: 2026-11-20
* 담당자: 확인 필요
* 대상 API: `GET /api/v1/orders/{id}`
* 수정 파일: `OrderController`, `OrderResponse`, `OrderService`
* 상세 내용: 응답 필드인 `totalPrice`의 데이터 타입을 문자열에서 숫자로 변경했다.

결과

* 프론트엔드 세 화면에서 합계가 정상적으로 계산되어 출력되었다.
* 단위 테스트 12건이 통과했다.

영향 범위와 확인 방법

* 영향 범위: `GET /api/v1/orders/{id}` API를 호출하는 프론트엔드 세 화면 및 관련 모듈 (`OrderController`, `OrderResponse`, `OrderService`)
* 확인 방법: 단위 테스트 실행 및 프론트엔드 세 화면에서 합계 계산 결과 확인 (상세 테스트 절차 확인 필요)
````

### 챗지피티 (무료 요금제)
````
주문 조회 API totalPrice 자료형 변경 기록
1. 기존 상황

* 주문 조회 API의 `totalPrice`가 문자열(String)로 반환됐다.
* 프론트엔드에서 합계를 계산할 때 문자열이 이어 붙는 오류가 발생했다.

2. 변경 내용

* 수정일: 2026-11-20
* 대상 API: `GET /api/v1/orders/{id}`
* 변경 사항: `totalPrice` 자료형을 문자열에서 숫자로 변경했다.
* 수정 파일:
   * `OrderController`
   * `OrderResponse`
   * `OrderService`

3. 결과

* 프론트엔드 세 화면에서 합계가 정상적으로 표시된다.
* 단위 테스트 12건이 통과했다.

4. 영향 범위

* 주문 조회 API의 응답 자료형
* `OrderController`, `OrderResponse`, `OrderService`
* 해당 API를 사용하는 프론트엔드 세 화면
* 추가 영향 범위는 확인 필요

5. 확인 방법

* 프론트엔드 세 화면의 합계 정상 표시 확인
* 단위 테스트 12건 통과 확인
* 추가 확인 항목은 확인 필요
````

## 6. 추가 실행: 모호한 입력 ("지시 재확인" 기준용)
입력: `쿠폰 로직을 고쳤다.` (시스템 프롬프트는 1차와 같고, 새 대화창에서 실행)

| 모델 | 실행 시점 (2차) |
|---|---|
| 클로드 | 2026-11-23 14시 30분 |
| 제미나이 | 2026-11-23 14시 31분 (클로드 1분 뒤) |
| 챗지피티 | 2026-11-23 14시 32분 (제미나이 1분 뒤) |

세 모델 모두 문서를 쓰지 않고 질문 세 개를 먼저 했다(되물음).

응답 원문만 싣는다. 복사하며 함께 붙은 입력 프롬프트는 1차와 같아서 뺐다. 제미나이는 화면에 응답 두 개(옵션 A, 옵션 B)를 함께 보여 주어 둘 다 싣는다.

### 클로드
````
문서를 쓰기 전에 질문 세 가지입니다.

1. 기존 상황: 쿠폰 로직에 어떤 문제가 있었나요? (예: 어떤 오류나 동작이 있었는지)
2. 변경 내용: 무엇을 어떻게 고쳤나요? (대상 API나 클래스, 변경일 포함)
3. 결과: 수정 후 어떻게 확인했나요? (예: 테스트 결과, 화면 동작)

답해 주시면 바로 작성하겠습니다.
````

### 제미나이
````
옵션 A
변경 기록 문서를 작성하기 전에 다음 사항을 먼저 확인해야 합니다.

1. 기존 상황: 쿠폰 로직에 구체적으로 어떤 문제나 버그가 있었습니까?
2. 변경 내용: 쿠폰 로직의 어느 부분(할인 계산, 유효기간 검증, 적용 대상 API 등)을 어떻게 수정했습니까?
3. 결과: 수정 후 테스트 통과 여부나 정상 작동 확인 결과는 무엇입니까?

옵션 B
변경 기록 문서를 작성하기 전에 필요한 내용을 먼저 확인합니다.

1. 기존 상황: 쿠폰 로직에 어떤 오류나 불편한 점이 있었는지 알려주세요.
2. 변경 내용: 쿠폰 로직에서 구체적으로 어떤 조건이나 동작을 수정했는지 알려주세요.
3. 결과: 수정 후 어떤 동작이 정상화되었거나 개선되었는지 알려주세요.
````

### 챗지피티
````
변경 기록을 작성하기 전에 정보 확인이 필요합니다.

1. 기존 상황: 쿠폰 로직에 어떤 문제가 있었나요?
2. 변경 내용: 쿠폰 로직을 어떻게 수정했나요? 대상 API나 수정 파일도 알려주세요.
3. 결과: 수정 후 정상 동작 여부나 테스트 결과가 있나요?
````
