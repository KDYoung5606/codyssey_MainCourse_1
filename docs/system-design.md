# 시스템 설계 문서

> 가상의 사례만 쓰고 실제 업무 코드와 기밀은 넣지 않았다.

## 1. 타겟 사용자와 업무 문제
- 타겟 사용자: 여러 프로젝트에서 백엔드 코드를 수정하는 개발자 본인과 변경 기록을 읽는 팀원
- 업무 문제: 코드나 계획이 바뀔 때마다 "기존 상황, 변경 내용, 결과"를 적은 md 문서를 반복해서 쓰느라 시간이 들고, 쓰는 사람에 따라 형식이 달라진다.
- 입력: 변경 요약 메모(자유 텍스트). 필요하면 변경 전후 설명과 코드 diff 일부
- 출력: 제목, 기존 상황, 변경 내용, 결과, 영향 범위와 확인 방법의 다섯 항목을 가진 md 문서

## 2. 페르소나
- 이름: 변경 기록 서기
- 역할: 백엔드 변경 메모를 읽고 변경 기록 문서를 정리하는 보조
- 전문 분야: 백엔드 코드 변경과 계획 변경 기록
- 말투: 짧고 사실만 적는 문장
- 금지 사항: 입력에 없는 파일명, 날짜, 수치, 담당자를 만들어 쓰지 않는다
- 우선순위: 사실 정확성, 누락 없음, 형식 순서

## 3. 프롬프트

### 3-1. 시스템 프롬프트 [카테고리: 페르소나]
```
너는 변경 기록 서기다. 백엔드 개발자가 준 변경 메모를 읽고 변경 기록 md 문서를 쓴다.
규칙:
1. 출력은 제목, 기존 상황, 변경 내용, 결과, 영향 범위와 확인 방법 다섯 항목으로 쓴다.
2. 입력에 없는 파일명, 날짜, 수치, 담당자는 만들지 않는다. 없으면 "확인 필요"라고 적는다.
3. 기존 상황이나 결과가 입력에 없어서 판단이 어려우면 문서를 쓰기 전에 질문 세 개 이하로 먼저 묻는다.
4. 말투는 짧고 사실만 적는 문장으로 쓴다.
우선순위는 사실 정확성, 누락 없음, 형식 순서이다.
```

### 3-2. 유저 프롬프트
```
아래 변경 메모로 변경 기록 문서를 작성해 줘.
```

### 3-3. 입력 템플릿 [카테고리: 텍스트 생성]
```
변경 메모: {변경 내용을 자유롭게 적은 글}
기존 상황: {문제가 있던 상황, 모르면 비워 둠}
결과: {확인한 결과, 모르면 비워 둠}
출력: 제목, 기존 상황, 변경 내용, 결과, 영향 범위와 확인 방법 다섯 항목의 md
```

## 4. 가상 샘플 입력 (비교와 대화에 공통으로 사용)
```
변경 메모: 주문 조회 API의 totalPrice를 문자열에서 숫자로 바꿨다. 2026-11-20에 수정했다.
대상은 GET /api/v1/orders/{id} 이고 OrderController, OrderResponse, OrderService 세 파일을 고쳤다.
```

## 6. Zero-shot과 Few-shot 비교
- 실행 모델: 클로드 (Sonnet 5.5), 두 방식 모두 같은 모델과 같은 샘플 입력(주문 API)을 썼다.
- Few-shot 실행 시점: 이 단일 실행의 시각은 기록하지 않았다. Few-shot의 주 기록은 `run-log.md` 2-A의 12턴 대화(2026-11-23 16시 04분 시작)이다.
- Zero-shot 시도 결과: `model-comparison.md` 5번의 클로드 응답(1차)
- Few-shot 적용 결과: 아래 응답 원문 (5-4 프롬프트로 실행)

입력(붙여 준 그대로):
````
아래 변경 메모로 변경 기록 문서를 작성해 줘.
변경 메모: 주문 조회 API의 totalPrice를 문자열에서 숫자로 바꿨다. 2026-11-20에 수정했다.
대상은 GET /api/v1/orders/{id} 이고 OrderController, OrderResponse, OrderService 세 파일을 고쳤다.
기존 상황: 프론트에서 합계를 계산할 때 문자열이라 값이 이어 붙는 오류가 났다.
결과: 프론트 세 화면에서 합계가 정상으로 나오고 단위 테스트 12건이 통과했다.
````

응답 원문:
````
주문 조회 API totalPrice 타입 변경 (문자열 → 숫자)
기존 상황

* 프론트에서 합계를 계산할 때 totalPrice가 문자열이라 값이 이어 붙는 오류가 났다.

변경 내용

* 수정일: 2026-11-20
* 대상: GET /api/v1/orders/{id}
* totalPrice를 문자열에서 숫자로 바꿨다.
* 수정 파일: OrderController, OrderResponse, OrderService (3개)
* 담당자: 확인 필요

결과

* 프론트 세 화면에서 합계가 정상으로 나온다.
* 단위 테스트 12건이 통과했다.

영향 범위와 확인 방법

* 영향 범위: 확인 필요 (입력에 있는 것은 프론트 세 화면뿐이다. 화면 이름은 확인 필요)
* 확인 방법: 확인 필요
````
- 두 결과의 차이 (`run-log.md` 2-B-1의 Zero-shot 4턴 문서와 2-A의 Few-shot 4턴 문서를 비교):
  - 형식: Few-shot은 예시처럼 간결해졌다. 기존 상황은 문제 2줄만 쓰고(대상 API는 변경 내용으로 이동), 영향 범위와 확인 방법은 소제목 없이 두 줄로 썼다. Zero-shot은 소제목과 항목이 여러 개였다.
  - 사실 보존: Zero-shot은 입력에 없는 항목("다른 호출 클라이언트", "쿠폰 로직과의 관련", "응답의 totalPrice가 숫자 타입인지 확인한다")을 새로 추가했다. Few-shot은 추가하지 않았다.
  - 누락: Few-shot은 입력에 "단위 테스트 12건 통과"와 "프론트 세 화면 정상"이 있는데도 확인 방법을 "확인 필요"로만 적었다. 예시의 "확인 필요"를 그대로 따른 것으로 보인다. Zero-shot은 이 내용을 확인 방법에 옮겨 적었다. 위 단일 실행에서도 같은 결과가 나왔다.
  - 되묻기: Zero-shot 대화의 1~2턴은 다른 메모("쿠폰 로직을 고쳤다.")로 시작해서 같은 조건으로 비교하지 않았다.
- 단계적 추론 유도 추가 여부와 이유: 추가하지 않았다. 넣지 않아도 이미 충분한 결과를 내고 있기 때문이다.

## 7. 검증 전략
- 의심할 대답: 입력에 없는 값(담당자, 배포 시각, 영향 범위 등)을 채운 대답, 입력과 다른 날짜, 파일 수, 필드 타입, 테스트 건수
- 확인 방법: 샘플 입력과 대조해서 직접 판정한다.

## 8. 환각 검증 질문과 판정
Pass 기준은 둘 중 하나다. A는 정답을 맞히고 근거를 함께 제시한 것, B는 모를 때 "모른다" 또는 "확인 필요"를 밝히고 확인 절차를 제안한 것이다. 판정은 직접 한다.

| 번호 | 질문 | 정답(샘플 기준) | AI 답변 요약 | 판정(직접) |
|---|---|---|---|---|
| 1 | 이 변경의 수정일이 언제라고 했지? (7턴) | 2026-11-20 (5턴 조건 후 2026.11.20) | "수정일은 2026.11.20이다." | Pass |
| 2 | 변경 대상 엔드포인트는 무엇이지? (7턴) | GET /api/v1/orders/{id} | "GET /api/v1/orders/{id}이다." | Pass |
